Security Model & Guardrails

A defense-in-depth architecture designed so an untrusted or hallucinating model cannot compromise your data. Every vector is validated across deterministic static analyzers, hardware envelopes, and PostgreSQL kernel-level roles.

01

Layered Defense Architecture

Incoming requests pass through an inverted filter funnel. If any single stage fails, the request halts instantly with machine-readable telemetry and no database execution.

vpn_key
Layer 1 •

OAuth 2.0 Scopes (Remote Mode only)

Token validation, JWT cryptographic signature verification, and mandatory scope containment.

db:read sheets:read sheets:write
arrow_downward
filter_list
Layer 2 •

Resource Allow-Lists

Strict environment-variable filters applied before SQL parsing. Accessing unlisted assets returns instant 404/Denied.

ALLOWED_SCHEMAS ALLOWED_TABLES ALLOWED_SHEET_IDS
arrow_downward
account_tree
Layer 3 •

SQL AST Inspection

Full abstract syntax tree tokenization. Strict single-statement enforcement. Immediate rejection of DDL, DML, and pg_* internals.

Strict SELECT Only
arrow_downward
layers
Layer 4 •

Read-Only Transaction Envelope

Hardware and engine isolation via wrapped transaction configuration: timeouts, process gating, and pagination envelopes.

MAX_ROWS=1000
BEGIN READ ONLY; SET statement_timeout = '15s'; SET max_parallel_workers_per_gather = 2;
arrow_downward
database
Layer 5 •

Underlying Database Role

Database-level least-privilege credentials. Even if every preceding layer were bypassed, the physical Postgres user cannot write.

REVOKE ALL PRIVILEGES

warning
Write Mode Protection Policy

Write tools are entirely invisible to the AI when READ_ONLY=true. When write mode is explicitly enabled, every state modification additionally requires an idempotency_key to block accidental query retries or double writes.
